Trading Conformance Agent: system architecture

A JSE Trading Operations analyst types a question about the July to September 2026 conformance test messages into a chat page. A language model on OpenRouter (a service that gives access to many language models) writes database queries; web/agent.js runs them on the gold tables inside the analyst's browser tab and returns the results to the model, and the model writes the answer. The project has no server of its own: every program runs in the browser tab or on an outside service.

Components

Chat page Agent, language model and reference Message data Code hosting Data build Dashed arrow: a reply

One question, step by step

If 12 rounds pass without answer text, agent.js sends one more request that tells the model to answer from the tool results it already has and to say which parts of the question it could not finish. That request does not allow tool calls. One reply from the model can contain several tool calls; agent.js runs each one and adds its result to the conversation before the next request.

Starting the page

  1. The browser downloads index.html and web/ from GitHub Pages.
  2. The analyst pastes the Supabase publishable key (starts sb_publishable_) into the sidebar.
  3. web/data.js downloads the DuckDB-WASM library from jsDelivr and starts it in a separate browser thread.
  4. It downloads gold/manifest.json, then each of the 9 Parquet files, from the bucket fix-data, and creates one table from each.
  5. It runs SET enable_external_access = false and SET lock_configuration = true, so the model's SQL can read only those 9 tables and cannot change the database's settings.
  6. The analyst pastes the OpenRouter key. The page can now take questions.

The 5 tools the model can call

ToolWhat agent.js doesReturns
list_tablesReads gold/manifest.jsonEvery table with its description, row count and column meanings
describe_tableReads the manifest and runs SELECT * … LIMIT 5 on the tableEach column's meaning, number of distinct values, number of empty values and most common values, and 5 sample rows
run_sqlPlaces the model's SELECT inside SELECT * FROM ( … ) LIMIT 201 and runs it on DuckDB-WASMAt most 200 rows, with a note when more rows exist
read_referenceDownloads one topic file from web/knowledge/: tests, field_codes, reject_codes, trading_sessions, orders, identifiers, gateway_rules or conformance_processThe text of the file, taken from JSE Volumes 00E, 01E, 10, 201 and 202
lookup_reject_codesLooks up the given codes in web/knowledge/reject_codes.jsonThe JSE Volume 10 meaning of each code, for codes not in dim_reject_code

The system prompt tells the model not to put SQL, table names, column names or tool names in its answer, and to describe what the messages show in plain words. The page shows only the answer text, not the tool calls.
