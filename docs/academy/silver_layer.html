Silver layer: 36 Excel exports combined into 11 tables

code/silver.py downloads the 36 Vonnegut exports from bronze/ in the Supabase bucket fix-data, puts every row of one FIX message type into one table, and uploads each table to silver/ as a Parquet file (a compressed file format for tables). No row is removed and no row is merged: the 11 tables hold the same 3,763,516 rows as the 36 files.

The letter or digit before each table's row count is the FIX message type code (FIX tag 35, MsgType) of every row in that table. The files in each row are joined by column name, so a column that one month's file does not have is empty for that month's rows.

* The July file named Logout [B].xlsx holds Logon Responses. silver.py chooses each file's table from the most common value in the file's Message Type column, which is B in this file, so its 4,312 rows are in logon_response, not logout.

What silver.py does to each file

  1. Downloads the file from bronze/. Every CompID in it is already fictitious: bronze.py replaced the real CompIDs before the upload.
  2. Changes each column header to lower case with underscores: Client Order ID becomes client_order_id. Reject files have two headers called Message Type; the second is the type of the client message that was rejected, and is named ref_message_type.
  3. Makes empty cells NULL (empty), and reads the timestamp column and every column ending in _time as a date and time. Vonnegut writes 24-hour times followed by an am or pm that is ignored, for example 2026-07-01 20:15:01.7941 pm.
  4. Keeps identifier and code columns as text, so that leading zeros and letters are kept: order_id, side, reject_code, time_in_force and every column whose name contains _id, code, type, status or a similar word. Any other column whose values are all numbers becomes a number column.
  5. Adds two columns: source_month (for example August_2026) and source_file (for example August_2026/Reject 3.xlsx).
  6. Adds the rows to the table for the file's message type. When all 36 files are read, each table is written to silver/<table>.parquet, and silver/manifest.json records each table's row count, columns and source files.

Silver keeps each export's own column names. Three pairs of columns hold the same field under two names: original_client_order_id and orig_client_order_id, orderbook and order_book, ordersubtype and order_sub_type. gold.py gives each pair one name when it builds fact_message (see Gold star schema). The network capture columns source, destination, bytes, sequence_no and packet_id are in silver only.

Why silver keeps every row

Vonnegut records many messages more than once, so silver row counts are higher than message counts: reject has 1,127,014 rows for 736,608 distinct messages. Silver keeps the repeated rows so that any rule for merging them can be checked against the exports. gold.py applies the merging rule and records in the column copies how many silver rows each message was made from.
